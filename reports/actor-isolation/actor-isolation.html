结论

在 AgentCore Memory 上可以做到“即使知道别人的 actorId，也读不到、写不进、删不掉别人的记忆”，并且由 AWS 在服务端强制：给每个用户签发带 actorId 标签的短期凭证，IAM 策略用 ${aws:PrincipalTag/actorId} 同时约束 actorId、namespace、namespacePath 三个条件键，并显式禁止没有 actor 级条件键的 API。

三个前提缺一不可：

  1. actorId 用不透明 ID，不含 /，否则 /u/alice/* 会匹配到 alice/x。
  2. 标签从已验签的用户 JWT 派生，不由业务代码随手填，否则后端传错 actorId 的 bug 会原样变成打错标签。
  3. Agent 自主调用记忆工具时走 AgentCore Gateway + Cedar 策略：Runtime 里所有用户共用一个执行角色，需要在 Gateway 按用户 JWT 校验。

方案对比

方案做法挡住代价 / 挡不住
A 应用层强制后端从登录态推导 actorId，客户端不传；Agent 工具不暴露 actorId 参数T1，T3（前提是工具不暴露参数）T2 无兜底；所有调用共用高权限角色
B IAM ABAC（本次实测）按用户签发带 actorId 标签的短期凭证，策略按标签约束三个条件键并禁止缺口 APIT1、T3–T6 由 AWS 强制；T2 取决于标签来源需要凭证签发并缓存（STS 默认共享配额约 600 RPS/账号/区域）；actorId 不能含 /
C Gateway + Cedar用户 JWT 进 Gateway，Cedar 要求 actorId == JWT sub、namespacePath == JWT namespace；Memory 只接受来自 Gateway 的请求T1–T6，以用户自己的 token 为准多一层 Gateway；IdP 需签发 namespace claim
D Cognito 主体标签客户端用 Cognito 换 AWS 凭证，属性映射为 principal tag，策略同 B同 B，标签来自 IdP客户端直连 AWS，暴露面更大
E 每租户一个 Memory按 Memory ARN 授权同 B只适合少量 B2B 租户

推荐：业务后端确定性读写用 A + B（标签由独立组件从 JWT 派生）；Agent 运行中自主调用记忆工具用 C。设计初稿经过一轮独立的反方评审，以上取舍来自那轮评审。

AgentCore 的 actorId 允许 /。额外创建 actor alice/x 后，它的记忆落在 /u/alice/x/…，正好被 Alice 的 /u/alice/* 匹配。以下请求都带着 Alice 的凭证：

这不是策略写错，而是 namespace 模板与 actorId 字符集的组合问题。解决办法是用 UUID 或 HMAC 生成不含 / 的 actorId，并在应用层强制校验。

对照：TDAM 能做到吗

TencentDB Agent Memory 的数据面只认一个共享的网关 Bearer key，user_id 由调用方自报。主评测中，持有这个 key 的调用方改一下 user_id，就读到了另一个用户的 12 条记录。要达到同等效果，只能在 TDAM 前面自建鉴权代理：从 JWT 推导 user_id 并覆盖请求，同时网关 key 不能下发到任何业务以外的组件。这相当于方案 A，没有服务端兜底。

落地清单

  • actorId 改为不透明 ID（UUID / HMAC），应用层正则校验，禁止 /、*、:
  • 凭证签发：从已验签 JWT 派生 actorId 标签（AssumeRoleWithWebIdentity / Cognito 主体标签 / 独立签发服务），按用户缓存到过期前 5 分钟
  • 上线上述 IAM 策略，配合 SCP 兜底禁止控制面操作
  • Agent 路径：Runtime 入站 JWT → Gateway Memory target + Cedar 策略；Memory 资源策略只允许 Gateway 访问；先用 LOG_ONLY 模式观察
  • 记录类 API 始终带 namespace 参数（不传会被拒）
  • 容量：估算峰值 STS 请求数并提前提额；监控 STS 与 Memory 的 Throttles
  • 把测试脚本纳入 CI，每次改策略都回归一遍
