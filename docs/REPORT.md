# 评测报告：TencentDB Agent Memory vs Amazon Bedrock AgentCore Memory

运行日期：2026-11-19 · 区域：us-east-1 · 运行名：`final`
原始汇总数据见 [`reports/final/`](../reports/final/)，每一个数字都能从 `summary.json` 或逐题 CSV 重新算出来。

## 结论先行

1. **记忆问答质量：AgentCore 明显领先。** 自建的 web3_zh 数据集共 120 题。AgentCore（Semantic + Preference + Summary）答对 96 题，正确率 **80.0%**（95% CI 72–86%）。TDAM 表现最好的配置答对 72 题，**60.0%**（51–68%）。配对 McNemar 检验中，只有 AgentCore 答对的题有 26 道，只有 TDAM 答对的有 2 道，p < 0.001。真正送进回答模型的 4K 上下文里，AgentCore 覆盖了 95.1% 的标注事实，TDAM 为 71.8%。
2. **TDAM 的多租户隔离需要使用方自己设计，任何一种拓扑都要付出代价。** TDAM v3 的 L2 场景和 L3 画像只按 `team + agent` 划分作用域，这是源码中明确写下的设计。所有终端用户共用一个 agent 时，30 个用户拿到的是**同一份**由全部用户对话合成的画像；给每个用户单独分配一个 team 可以隔离画像，但同样的对话抽出的 L1 少了 26%（381 vs 518，两次检查时 L1 队列都已清空），正确率降到 40%。AgentCore 按 `actorId` 划分 namespace，不存在这个取舍。
3. **身份隔离：AgentCore 可以用 IAM 强制，TDAM 依赖应用层自觉。** TDAM 的数据面只用一个共享的 Bearer key，调用方改一下 `user_id` 就能读到别人的记忆（实测可读）。AgentCore 给 IAM 角色加上 `bedrock-agentcore:namespace` 条件后，访问其他租户直接返回 `AccessDenied`（实测）。
4. **写入后多久可检索：AgentCore p50 10.5 秒、最慢 21 秒（6/6）；TDAM 在 30 分钟内 0/6。** 这项只测了 6 个用户、一种对话（产品咨询中夹带一句"帮我记一下邀请码"）。TDAM 的抽取器对这类会话返回 `empty_scenes`，邀请码一直停在原始对话层（L0）。在主数据集上 TDAM 能正常抽取，所以这一条应理解为"特定对话形态下会漏记"。另外，即便抽取正常，TDAM 默认也要等 ≥600 秒的空闲超时才会处理最后几轮。
5. **AgentCore 有一项明显的反例：密钥会进入长期记忆。** 数据集里每个用户都贴了一个假 API secret，AgentCore 内置策略在 30/30 个用户的长期记忆里原样保存了它，TDAM 是 0/30。生产环境使用 AgentCore 时，必须在 `CreateEvent` 之前脱敏，或者使用自定义策略 prompt / Guardrails。
6. **并发检索：低并发时两者在同一量级；高并发时 AgentCore 先撞上账户默认配额。** 并发 1 时，TDAM 的 p50 为 0.09–0.13 秒，AgentCore 为 0.17–0.19 秒。`RetrieveMemoryRecords` 的默认配额是每账户 30 TPS（可申请提升）。三策略并行检索每个请求要调 3 次 API；并发 8 以上时 CloudWatch 记录到了 Throttles（每分钟 5–38 次），随后 boto3 的 adaptive 重试模式在客户端主动降速，表现为秒级延迟，但没有报错。改成一次分层检索（`agentcore_path`）后，质量基本不变（76/100 vs 78/100），调用量降到 1/3。生产上线前需要申请提额。
7. **成本（口径不同，仅供量级参考）：** AgentCore 这次运行约 **$1.56**，其中包含 1,832 条长期记录一个月的存储费；TDAM 抽取 30 个用户历史的内部 LLM 和 embedding 费用约 **$2.6**，这是一次性的（两种拓扑合计 $5.25，Haiku 输入 token 是原始对话的 50 倍以上），另外还要加上 EC2/EBS、高可用和运维人力。

> 一句话：在这个交易所助手场景里，AgentCore 的记忆质量更高，隔离由 IAM 保证，写入后 10–20 秒即可检索，并且不需要运维；需要额外处理的是敏感信息脱敏和检索配额。TDAM 在本地数据主权、单机低延迟、即时删除和"不把密钥写进记忆"这几点上表现更好。

## 1. 被测配置

| 项 | TDAM | AgentCore |
|---|---|---|
| 版本 | `agentmemory/memory-core@sha256:342331d5…`（2026-10-26），源码分支 `feat/server_team` | Bedrock AgentCore Memory（托管服务） |
| 部署 | 独立 EC2 m7i.xlarge，standalone + SQLite，Docker | 托管，同区域 API |
| 抽取 | Claude Haiku 5.5（经 LiteLLM 提供 OpenAI 兼容接口），`promptMode: chat` | 内置策略（模型由服务托管） |
| 检索 | BM25（jieba）+ Titan V2 向量 + RRF | 语义检索，Semantic / UserPreference / Summary 三个 namespace |
| 组装 | `tdam_full` = L3 persona + L2 scene navigation + L1（复刻原生 auto-recall）；`tdam_l1` = 只用 L1 | 三个 namespace 结果按名次交错合并；`agentcore_path` = 一次分层检索 |
| 拓扑 | `tdam_*`：每个用户一个 team（画像私有）；`tdam_shared_*`：所有用户共用一个 team | 每个用户一个 actorId |

所有 arm 共用：回答模型 Haiku 5.5、评分模型 Sonnet 5.5（LongMemEval 官方模板，要求最后一行输出 `VERDICT`）、4,096 tokens 上下文预算、候选上限 50（`config.yaml: top_k`）。
runner 是另一台 EC2，通过 VPC 私网访问 TDAM，访问 AgentCore 走同区域公共端点。每一项配置差异和理由都列在 [CONFIG_DIFF.md](CONFIG_DIFF.md)。

## 2. 记忆质量

### 2.1 web3_zh（120 题，30 个用户 × 8 会话，中文为主、夹带英文）

| arm | 答对/题数 | 正确率 | 95% CI | 4K 事实覆盖 | 上下文 tokens | 检索 p50 / p95（秒） |
|---|---:|---:|---:|---:|---:|---:|
| none（无记忆） | 17/120 | 14.2% | 9–22% | — | 0 | — |
| tdam_full | 43/120 | 35.8% | 28–45% | 47.6% | 2,411 | 0.153 / 0.241 |
| tdam_l1 | 48/120 | 40.0% | 32–49% | 47.2% | 662 | 0.149 / 0.178 |
| tdam_shared_full | 37/120 | 30.8% | 23–40% | 70.9% | 3,021 | 0.154 / 0.190 |
| tdam_shared_l1 | 72/120 | 60.0% | 51–68% | 71.8% | 965 | 0.137 / 0.177 |
| **agentcore_spu** | **96/120** | **80.0%** | **72–86%** | **95.1%** | 4,078 | 0.192 / 0.282 |

分类别：

| arm | 拒答 | 跨语言 | 事实 | 跨会话 | 偏好 | 时间 | 更新 |
|---|---:|---:|---:|---:|---:|---:|---:|
| none | 17/17 | 0/17 | 0/18 | 0/17 | 0/17 | 0/17 | 0/17 |
| tdam_full | 17/17 | 12/17 | 6/18 | 5/17 | 1/17 | 0/17 | 2/17 |
| tdam_l1 | 17/17 | 12/17 | 6/18 | 5/17 | 4/17 | 2/17 | 2/17 |
| tdam_shared_full | 17/17 | 3/17 | 2/18 | 0/17 | 2/17 | 4/17 | 9/17 |
| tdam_shared_l1 | 17/17 | 15/17 | 13/18 | 10/17 | 4/17 | 4/17 | 9/17 |
| agentcore_spu | 17/17 | 17/17 | 18/18 | 15/17 | 7/17 | 5/17 | 17/17 |

几点观察：
- **知识更新（白名单地址换绑）差距最大**：AgentCore 17/17，TDAM 最好 9/17；对应地，TDAM 的 4K 事实覆盖也只有 72%。
- **TDAM 的 `full` 比 `l1` 差**：L3 persona 和 L2 导航会占用上下文；共享拓扑下注入的画像还是全体用户共用的同一份（见 §3），跨语言题从 15/17（`l1`）降到 3/17（`full`）。我们没有逐题归因，画像混入他人信息是最可能的原因，但未做验证。
- **偏好题对两者都难**（评分要求回答至少用到两条偏好，并且不违背任何一条）。
- **时间题主要受数据集歧义影响**："下周X" 是在周中说的，标准答案按"周一开始的下一周"计算，但很多记忆把它解析成了最近的那个 X。用确定性的日期匹配来看：AgentCore 有 13/17 道题给出了标准日期或标准日期 −7 天（其中 10 道是 −7 天），TDAM 为 5–7 道。表中保留的是原始评分。

## 3. 多租户与安全

| 测试 | TDAM | AgentCore |
|---|---|---|
| 调用方配置正确时的跨租户泄漏（90 次探测，查询里直接带上别人的独有 token） | 0/90（两种拓扑都是） | 0/90 |
| 同一 team+agent 下的画像共享 | **30 个用户注入的是同一份 persona/scene**（共享拓扑） | 不适用（按 actor 划分 namespace） |
| 伪造 `user_id` 越权读取 | **可以**：持有网关 Bearer key 的调用方读到了另一个用户的 12 条 L1 记录 | **拒绝**：IAM 角色条件为 `bedrock-agentcore:namespace` = `/u/A/*`，读 `/u/B/` 返回 `AccessDenied` |
| 假 API secret 是否进入长期记忆 | 0/30 | **30/30**（原样保存） |
| 未带 Bearer 访问数据面 | 401（前提是配置了 key；官方 `start-memory-core.sh` 里 `MEMORY_CORE_GATEWAY_API_KEY` 默认为空，启动日志会提示所有路由对网络开放） | 必须 SigV4 签名 |
| 静态加密 / 审计 | 由使用方负责（SQLite 文件放在主机磁盘上，加密取决于卷的配置；API 审计需要自己搭建） | 托管加密，`CreateMemory` 支持 `encryptionKeyArn`（CMK）；API 调用记录在 CloudTrail |

说明：
- IAM 条件只对精确的 `namespace` 参数生效。使用 `namespacePath` 时条件键不会被填充，因此连本租户的请求也会被拒绝（失败时是关闭的，不会放行）。做按租户的 IAM 隔离时，检索要用精确的 namespace。
- 伪造身份的测试在开发环境（同一镜像和服务版本）中完成，结果见 `reports/final/spoof_dev.json`。

## 4. 时延与吞吐

### 4.1 写入→可检索（6 个新用户，邀请码出现在 6 轮对话的第 3 轮）

| | 6 个里可检索的数量 | p50 | 说明 |
|---|---:|---:|---|
| AgentCore | 6/6 | 10.5 秒（p95 21 秒） | 语义检索能直接查到 |
| TDAM | 0/6（30 分钟内） | — | L1/L2/L3 都是 0，抽取器日志为 `l1-empty reason=empty_scenes`；原始 L0 能搜到，但原生 recall 不使用 L0 |

主数据集上也能看到同样的情况：TDAM 写入后先要等 600 秒空闲超时；L2 场景抽取基本是串行的，60 个用户的历史导入后，L2 队列积压到 302 个任务、同时只跑 1 个，一小时以上都没有清空。

### 4.2 写入调用时延

| | p50 | p95 |
|---|---:|---:|
| TDAM `conversation/add`（每轮一次，同步计算 L0 embedding） | 0.233 秒 | 0.321 秒 |
| AgentCore `CreateEvent`（每 ≤20 条消息一次） | 0.079 秒 | 0.109 秒 |

### 4.3 检索压测（closed-loop，每档 45 秒，0 错误）

| arm | 并发 1：p50 / p95，rps | 并发 8 | 并发 32 |
|---|---|---|---|
| tdam_l1 | 0.133 / 0.174，7.3 | 0.131 / 0.200，54 | 0.383 / 0.540，80 |
| tdam_full | 0.093 / 0.115，9.5 | 0.125 / 0.188，58 | 0.400 / 0.515，77 |
| agentcore_spu（每请求 3 次调用） | 0.190 / 0.296，4.3 | 0.49 / 20.8，1.3 | 8.1 / 33.5，2.4 |
| agentcore_path（每请求 1 次调用） | 0.174 / 0.231，5.5 | 0.220 / 2.33，12.9 | 0.534 / 17.3，11.2 |

`agentcore_path` 的问答质量是在删除探针之后评估的，因此只统计仍保留数据的 25 个用户（100 题）：答对 76/100，同一批题上 `agentcore_spu` 为 78/100（只有其中一方答对的题为 2 vs 4），4K 覆盖 93.4% vs 94.6%。逐题 CSV 已剔除被删除的 5 个用户。

解读：AgentCore 在并发 8 以上的时间窗口内，CloudWatch `Throttles`（Operation=RetrieveMemoryRecords）每分钟记录到 5–38 次；被接受的调用只有每秒 5–13 次，低于 30 TPS。原因是 boto3 的 adaptive 重试模式在收到限流后会在客户端主动降低发送速率，结果就是延迟升高但没有报错。所以这几档反映的是**默认配额加客户端退避**的组合。提额以后能到多少，本次没有测，需要提额后复测。TDAM 单节点在 32 并发下 0 错误（p99 0.64 秒，最大 8.6 秒），但它只有一个节点：节点本身挂掉会怎样，见 §5。

## 5. 删除与可靠性

| 测试 | TDAM | AgentCore |
|---|---|---|
| 删除用户后的残留（各 5 个用户，0/30/120 秒检查） | 0 秒时即无残留；API 耗时 0.2 秒/用户（需要分别删 L1/L0/L2/L3 四类） | 0 秒时仍能检索到；30 秒时 4/5 已清零，120 秒时 5/5 清零（最终一致）；1.4 秒/用户（记录 + 事件） |
| 写入重试是否幂等 | **不幂等**：一次进程重叠导致 12 个用户的轮次被重复写入，只能清库重来 | `clientToken` 保证幂等 |
| 容器重启（并发 4 的负载中执行 `docker restart`） | 0/3,829 失败（客户端重试 4 次），记录 445 → 445，没有丢失 | 托管服务，不需要做这项测试 |
| 单机 / 可用区故障 | 单点：SQLite 跑在单台主机上，高可用要自建（MongoDB 后端是实验特性） | 区域级托管服务 |

## 6. 成本（本次运行，按公开价格估算，不是账单）

| | AgentCore | TDAM |
|---|---|---|
| 记忆服务本身 | STM 写入 240 个事件 ≈ $0.003；1,832 条长期记录 ≈ $1.37/月；360 次检索 ≈ $0.18 | 内部 LLM + embedding：两种拓扑合计 $5.25（Haiku 输入 28.9M / 输出 3.7M tokens，Titan 0.65M tokens），即每 30 个用户约 $2.6 |
| 基础设施 | 无 | EC2 m7i.xlarge $0.2016/小时（约 $147/月）+ EBS；高可用时翻倍 |
| 运维 | 无 | 升级、备份、监控、LLM 网关、密钥轮换 |

两边的费用口径不同：AgentCore 一栏包含一个月的存储费，TDAM 一栏是一次性的抽取费用。

规模估算的方法：AgentCore 的费用 ≈ 记录数 × $0.75/千条/月 + 检索次数 × $0.50/千次 + 事件 × 12KB × $1/GB；TDAM 的费用 ≈ 原始对话 token × 约 50（抽取放大系数）× LLM 单价 + 主机。两者都可以代入自己的流量和单价，直接用 `config.yaml` 里的 `pricing` 计算。

## 7. TDAM 做得好的地方

- **单机检索很快**：p50 约 0.1 秒，32 并发下 80 rps 没有报错，适合低延迟、可控规模的场景。
- **不会把密钥写进长期记忆**（0/30），这一项比 AgentCore 默认策略更稳妥。
- **删除立即生效**，而且所有数据都在自己的主机上，数据主权完全可控。
- **记忆资产化**：除了 Chat Memory，还有 Skill、Wiki、CodeGraph、团队共享和 ACL，面向的是"团队型 Agent"场景，这部分不在本次评测范围内。

## 8. 局限
- 样本量：120 + 7 题。分类别的数据每类只有 17 题，只能看方向。
- TDAM 测的是 standalone + SQLite；腾讯云托管版本（TCVDB 后端）未测。TDAM 的抽取模型可以换成更强的 Sonnet，但成本也会上升。
- 托管服务的抽取模型不可控；AgentCore 的检索结果在强并发下受账户配额影响。
- web3_zh 是 LLM 生成的合成对话（事实和答案由 schema 确定性生成）；时间题存在"下周X"的歧义，已单独做了敏感性分析。
- 评分模型对偏好题较严格。所有 arm 用的是同一个评分模型，相对比较仍然有效。
