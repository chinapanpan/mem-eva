# 评测报告：TencentDB Agent Memory（TDAM）vs Amazon Bedrock AgentCore Memory

修订版 · 2026-11-20 · us-east-1 · 运行名 `paced`（初版 `final`，2026-11-19，保留作对照）
数据来源：问答质量、隔离 / 密钥 / 删除探针、写入耗时和成本来自 [`reports/paced/`](../reports/paced/)；检索压测、容器重启和 LongMemEval 来自 [`reports/final/`](../reports/final/)；连续更新测试来自 [`reports/chain2/`](../reports/chain2/)；用户隔离测试来自 [`reports/actor-isolation/`](../reports/actor-isolation/)。TDAM 就绪过程中的计数记录在原始运行目录里（未公开，可复跑得到）。

> **修订说明**：初版向 TDAM 写入历史对话时逐轮背靠背写入，间隔约 0.3 秒。这触发了 TDAM 抽取调度的时序问题，部分轮次没有被抽取，TDAM 被明显低估，初版“AgentCore 领先 20 个百分点”的结论作废。修订版两边都按每轮（一问一答）20 秒写入，TDAM 两种拓扑各用独立实例，回答上限提高到 2,000 tokens。第 6 节给出初版与修订版的逐项对照。

## 结论先行

1. **按真实节奏写入时，两边的记忆问答质量很接近。** web3_zh 共 120 题：
   - AgentCore SPU 答对 94 题（78.3%，95% CI 70–85%），单次分层检索答对 98 题（81.7%）。
   - TDAM 最佳配置答对 89 题（74.2%，66–81%）。
   - 配对 McNemar 检验：只有 AgentCore 答对的 10 题，只有 TDAM 答对的 5 题，p = 0.30，**差异不显著**。
   - 4K 事实覆盖率：AgentCore 96.8%，TDAM 92.2%。
2. **知识更新上 AgentCore 更稳，但只能看方向。** 白名单地址被换掉后再问，AgentCore 17/17，TDAM 12–13/17，只差 4–5 题。在单独的连续更新测试里（同一个地址先写入、再改 9 次），两边原生方式都是 10/10。
3. **AgentCore 的新信息生效更快。** 一段短对话写完后，AgentCore 约 76 秒就能检索到，TDAM 约 616 秒，因为它在等 600 秒空闲触发。对话持续进行时，TDAM 会按轮数提前抽取，空闲超时也可以调小。
4. **用户隔离：AgentCore 可以由 AWS 在服务端强制，TDAM 只能靠应用层。**
   - AgentCore 用 IAM ABAC：凭证带 `actorId` 标签，策略同时约束 `actorId` / `namespace` / `namespacePath`。我们实测了 25 种越权方式，全部被拒，单次分层检索也能用。
   - TDAM 的数据面只认一个共享 key，改 `user_id` 就能读到别人的记忆。共享 team 拓扑下，30 个用户只分到 3 份由多人对话合成的画像。
5. **AgentCore 的短板：密钥会进入长期记忆**（30/30，TDAM 0/30）；删除是最终一致的，120 秒内清零，TDAM 立即生效。
6. **检索性能**：单次检索 TDAM 稍快（修订版评估中 p50 0.135–0.154 秒 vs 0.178–0.188 秒）。初版压测中，并发 8 以上 AgentCore 受默认 30 TPS 配额限制，需要提额。
7. **成本**（30 个用户、口径不同，只看量级）：AgentCore 约 $1.02/月存储 + $0.18 检索；TDAM 内部 LLM 每种拓扑约 $2.9（一次性），另加 EC2/EBS、高可用和运维。
8. **两边都要控制批量导入的节奏**：写得太快，TDAM 会少抽记忆，AgentCore 会触发抽取配额限流（初版导入 LongMemEval 时失败任务最多同时有 441 个）。

## 1. 被测配置

| 项 | TDAM | AgentCore |
|---|---|---|
| 版本 | `agentmemory/memory-core@sha256:342331d5…`（2026-10-26） | Bedrock AgentCore Memory（托管） |
| 部署 | 一台 EC2 m7i.xlarge 上两个容器：8420（每用户一个 team）/ 8421（共享 team），standalone + SQLite | 托管，同区域 API |
| 抽取 | Claude Haiku 5.5（经 LiteLLM 提供 OpenAI 兼容接口），`promptMode: chat`，Titan V2 embedding | 内置 Semantic / User Preference / Summary 三种策略（模型由服务托管） |
| 写入 | 每轮一次 `conversation/add`，间隔 20 秒 | 每轮一个 `CreateEvent`，间隔 20 秒 |
| 检索 | `tdam_full` = L3 画像 + L2 场景导航 + L1（复刻原生 auto-recall）；`tdam_l1` = 只用 L1 | `agentcore_spu` = 三个 namespace 并行检索后交错合并；`agentcore_path` = 单次分层检索 |

所有方案共用以下设置：
- 回答模型：Haiku 5.5，输出上限 2,000 tokens；
- 评分模型：Sonnet 5.5，用 LongMemEval 官方模板，要求最后一行输出 `VERDICT`；
- 上下文预算 4,096 tokens，候选上限 50。

配置差异见 [CONFIG_DIFF.md](CONFIG_DIFF.md)。

## 3. 多租户与安全

| 测试 | TDAM | AgentCore |
|---|---|---|
| 调用方配置正确时的跨租户泄漏（90 次探测） | 0/90（两种拓扑） | 0/90 |
| 共享 team+agent 时的画像 | 30 个用户只有 3 份由多人对话合成的画像 | 不适用（按 actor 划分 namespace） |
| 知道别人的 ID 能否读其记忆 | 能：共享 Bearer key，改 `user_id` 就读到了别人的 12 条记录 | 默认权限下也能；用 IAM ABAC 后 25/25 种越权尝试全部被拒（见 [ACTOR_ISOLATION.md](ACTOR_ISOLATION.md)） |
| 假 API secret 是否进入长期记忆 | 0/30 | **30/30** |
| 未带凭证访问数据面 | 401（前提是配置了 key；官方 `start-memory-core.sh` 默认 key 为空） | 必须 SigV4 签名 |
| 静态加密 / 审计 | 由使用方负责 | 托管加密，`CreateMemory` 支持 `encryptionKeyArn`；API 调用记录在 CloudTrail |

## 4. 写入→可检索时延

数据来自连续更新测试，计时从最后一次写入调用返回开始，到检索结果中出现新值为止。每轮只写一段 3 轮的短对话然后空闲，所以 TDAM 只能靠 600 秒空闲超时触发抽取。

| | 生效 | p50 | 最慢 |
|---|---:|---:|---:|
| AgentCore | 10/10 | 76 秒 | 77 秒 |
| TDAM | 10/10 | 616 秒 | 618 秒 |

写入接口本身的耗时（只是接口返回，不代表可检索）：AgentCore `CreateEvent` p50 0.072 秒、p95 0.109 秒；TDAM `conversation/add` p50 0.239 秒、p95 0.715 秒。

初版的写入→可检索探针（6 个用户，TDAM 0/6）同样是背靠背写入，结果无效，已作废。

## 5. 检索性能（只测检索调用本身，沿用初版）

检索压测在数据写入、抽取完成之后进行，与写入节奏无关。

| arm | 每请求调用 | 并发 1：p50 / p95，吞吐 | 并发 8 | 并发 32 |
|---|---:|---|---|---|
| tdam_l1 | 1 | 0.133 / 0.174 秒，7.3 rps | 0.131 / 0.200 秒，54 rps | 0.383 / 0.540 秒，80 rps |
| tdam_shared_l1 | 1 | 0.094 / 0.124 秒，10.4 rps | 0.137 / 0.208 秒，53 rps | 0.440 / 0.640 秒，69 rps |
| tdam_full | 3（并行） | 0.093 / 0.115 秒，9.5 rps | 0.125 / 0.188 秒，58 rps | 0.400 / 0.515 秒，77 rps |
| agentcore_spu | 3（并行） | 0.190 / 0.296 秒，4.3 rps | 0.490 / 20.8 秒，1.3 rps | 8.1 / 33.5 秒，2.4 rps |
| agentcore_path | 1 | 0.174 / 0.231 秒，5.5 rps | 0.220 / 2.33 秒，12.9 rps | 0.534 / 17.3 秒，11.2 rps |

所有档位都是 0 错误。AgentCore 在并发 8 以上时，CloudWatch `Throttles`（Operation=RetrieveMemoryRecords）每分钟记录到 5–38 次：账户默认配额是 30 TPS，boto3 的 adaptive 重试会在客户端主动降速，所以表现为高延迟、不报错。提额后的表现本次没测。

## 6. 初版与修订版对照

| arm | 初版（背靠背写入，回答上限 800） | 修订版（每轮 20 秒，上限 2,000） | 4K 覆盖：初版 → 修订版 |
|---|---:|---:|---:|
| tdam_l1 | 48/120 | **89/120** | 47.2% → 92.2% |
| tdam_full | 43/120 | **89/120** | 47.6% → 92.2% |
| tdam_shared_l1 | 72/120 | 88/120 | 71.8% → 94.2% |
| tdam_shared_full | 37/120 | 66/120 | 70.9% → 94.2% |
| agentcore_spu | 96/120 | 94/120 | 95.1% → 96.8% |

AgentCore 两次基本不变，TDAM 大幅上升，说明初版的差距主要来自写入方式对 TDAM 的影响。修订版中，TDAM 每用户一个 team 时抽出的 L1 记忆为 622 条（初版 381 条），共享 team 时为 636 条（初版 518 条）。

先做的 24 题对照实验和这个结果一致：同一 TDAM 镜像与配置，只改写入间隔，`tdam_l1` 从 13/24 升到 21/24，L1 从 76 条升到 121 条。

## 9. 局限

- **样本量**：120 + 7 题。总体差距在统计误差范围内，分类别结论只能看方向。
- **未覆盖的范围**：
  - TDAM 的腾讯云托管版；
  - AgentCore 提额后的并发表现；
  - Gateway + Cedar 隔离路径（只做了方案分析）；
  - LongMemEval 按新节奏重跑。
- **写入节奏**：20 秒一句是对真实聊天的近似。批量导入历史时写入更快，TDAM 会少抽记忆，这是选型时需要考虑的因素。
- **数据集**：web3_zh 是合成对话，时间题有歧义。
- **TDAM 就绪**：共享 team 实例等到了 60 分钟上限仍未完全稳定，`tdam_shared_full` 可能偏低。
